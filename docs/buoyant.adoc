= Buoyant

== Summary

I discovered the Buoyant crate, which simplifies embedded graphics rendering.
Rather than explicitly define each shape with exact pixel values, Buoyant provides an interface more similar to SwiftUI or Jetpack Compose.
This was immediately appealing to me.
I hated all the work that went into arranging the one screen I made for the watch so far, and would not have continued to develop the project without a library to simplify things.

Unfortunately, when I tried Buoyant, I discovered a bug that made it unusable in my code.
When Buoyant renders to a target, it first checks if it needs to clip the image, and then renders to it.
Previously, the framework only stored the size of the render target, and assumed the origin was (0, 0).
This worked fine for most use cases, but for the RAM constrained PineTime, I had to render in multiple passes, so only the first one worked correctly.

== PineTime Hardware Constraints

The PineTime uses an nRF52832 with 64K of RAM.
It also has a 240x240 screen that uses RGB565 color format.

If you do the math, 240 pixels wide x 240 pixels tall x 2 bytes/pixel = 115,200.
It would take almost twice as much RAM as we have to make a full framebuffer for the display.
Since I can't use a full framebuffer, I use a 240x20 framebuffer which only takes 9.6K.

== The Issue

When I started testing Buoyant, I ran into a strange issue.
The images and shapes only rendered correctly on the first pass of the framebuffer.

I ran a few simple tests to verify this.
I increased and decreased the framebuffer size and the portion of the screen that rendered correctly changed accordingly.

I knew it was a bug in Buoyant because my rendering worked exactly as expected for plain embedded-graphics.

== Workaround Attempt

If the problem stems from Buoyant's interactions with framebuffers, one solution would be to get rid of the framebuffer.
We can use the blocking display crate to render directly into the display and potentially bypass the issue.

Unfortunately, when attempting this, I quickly ran into other constraints.
Drawing to the display will not erase anything that is already there, so we need to explicitly draw backgrounds.
We could either add the backgrounds to the Buoyant view, or send a clear command to the display.
Either option splits the draw into two steps and since the nRF52832's SPI bus is limited to 8 Mbps, the display is slow enough to update that there is a very noticeable flicker.

In the end, the framebuffer is needed so that multiple draws in a single frame do not cause flickering.

== The Solution

At this point, my best guess on the source of the issue was that Buoyant attempted to draw everything on the first pass, then on subsequent passes, assumed the shapes were already drawn and skipped them.
I had to put the project on hold for a while, but when I came back, the first thing I did was check for updates to Buoyant.
After updating to the latest commit and rebuilding, my bug was gone, so I began investigating to find out what changed.

Commit 14ffaa9 was the only one that mentioned image rendering, so that was my first guess where to look.
I quickly verified this by testing a build on that commit and the previous one.

This commit changed the behavior of render targets.
Now, they store their bounds as a rectangle with an origin that can be non-zero, rather than just a size.

[source,rust]
----
-    fn size(&self) -> Size;
+    /// The region this surface permits drawing in.
+    ///
+    /// The origin is not necessarily zero.
+    fn bounding_box(&self) -> Rectangle;
+
+    /// The size of the region this surface permits drawing in.
+    fn size(&self) -> Size {
+        self.bounding_box().size
+    }
----

Buoyant had previously been using the same region, (0, 0, 240, 20), to clip each shape during rendering.
This was correct only on the first pass of the framebuffer, all other draws had no overlap between the framebuffer and the region used for clipping, so the entire image was clipped.
Now, Buoyant stores and then clips to the correct region, (0, y, 240, 20), on each pass of the partial framebuffer, rendering the image as expected.

Rather than skipping the shapes like I guessed, Buoyant was simply clipping them wrong.
This makes sense in hindsight and I can see how this slipped under the radar for so long.
A project using embedded-graphics-simulator, a full framebuffer, or drawing directly to the display would all have no issues.
Especially during development, there would be no reason to draw to a target with any origin other than (0, 0).
It is only the specific use case of a partial framebuffer that reproduces the bug.
